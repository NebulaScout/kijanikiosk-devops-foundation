# Hardening Decisions

This week’s hardening choices aim to reduce accidental exposure while keeping the system simple enough to operate. The guiding idea is to limit who can reach each service, make administrative access depend on a private key pair rather than shared credentials, keep infrastructure state in a place that can be tracked consistently, and lock down the service runtime so a compromise has less room to spread. The result is not perfect isolation, but it is a clear step toward a smaller attack surface and more predictable operations.

| Control | What it does | Risk mitigated |
| --- | --- | --- |
| Shared security group for the server fleet | Places the application servers behind one consistent network boundary so access rules are managed in one place. | Prevents drift between servers and lowers the chance of one instance being exposed differently from the others. |
| Inbound access for web traffic only | Allows only the public traffic needed for the application to function. | Reduces the number of reachable services and narrows the chance of an unnecessary port being abused. |
| Administrative access through a key pair | Requires a pre-issued key for remote administrative login instead of relying on shared passwords. | Lowers the risk of password guessing, credential reuse, and casual account sharing. |
| Key pair name passed as an explicit setting | Makes the selected key pair part of the deployment inputs rather than something chosen ad hoc during setup. | Reduces configuration mistakes and helps keep access consistent across environments. |
| Remote state stored locally for this phase | Keeps the infrastructure record in a single state file so changes are visible and reproducible during the lab exercise. | Reduces confusion about what is deployed and lowers the chance of hidden, unmanaged changes. |
| Tagged managed resources | Marks the servers as infrastructure managed by the provisioning layer. | Improves traceability and makes it easier to spot resources that were created outside the intended process. |
| NoNewPrivileges and empty capability sets | Prevents the service from gaining extra privilege after start and removes ambient capability grants. | Limits the damage an exploited service can do if the process is compromised. |
| Private temporary space and private devices | Gives the service isolated temporary storage and blocks direct access to device resources. | Reduces lateral abuse of shared system areas and makes the service depend on fewer host features. |
| Strict system protection for the service tree | Treats the application’s files as protected from routine writes while the service is running. | Makes unauthorized modification harder and helps preserve the integrity of deployed content. |
| Home, namespace, and realtime restrictions | Prevents the service from using sensitive home areas, creating new namespaces, or using realtime scheduling. | Limits breakout techniques and removes capabilities that are not needed for a simple web workload. |
| Architecture and capability constraints | Forces the service to use the native instruction set and an empty capability envelope. | Shrinks the set of execution paths and keeps the process from carrying unnecessary powers. |

These decisions are intentionally layered. The network boundary keeps most traffic away from the instances, the key pair keeps administrative entry tied to a deliberate credential, remote state keeps the infrastructure record coherent, and the service directives make the runtime less trusting by default. None of those controls depends on a single perfect setting; they reinforce one another, which is the point of hardening.

There is also a practical reason for choosing controls at these layers instead of trying to solve everything in one place. The network rules answer the question of who may talk to the server at all. The access key answers who may administer it. The service restrictions answer what the process may do after it starts. State management answers how the team knows what was built and changed. When those questions are separated cleanly, reviews are faster, troubleshooting is easier, and the team can spot gaps sooner. That matters for Nia because the goal is not to make the system look secure on paper; it is to make the next change safer than the last one.

The main tradeoff is that the deployment is still approachable for a small team. We did not introduce a complex firewall design, a secret management platform, or a highly segmented identity model. Instead, we chose controls that are easy to explain, easy to verify, and hard to misread. That makes the posture more reliable for the current stage of the project, especially when the team is still changing the infrastructure regularly.

What this posture does not protect against is a determined attacker who gets valid access, a vulnerable application that already runs with the expected privileges, or mistakes made in the deployed code itself. It also does not stop misuse of exposed web entry points, compromise of the private key outside the system, or weaknesses in external dependencies. The hardening here reduces blast radius and basic exposure, but it does not replace patching, review, monitoring, and application-level security work.
