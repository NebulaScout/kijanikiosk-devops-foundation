# Comparison for Nia

This summary is written for a board audience, so it stays focused on what changed for the business rather than how the system is wired. The two approaches solve different problems. The first is strongest when the main goal is to move traffic safely from one live version to another with very little user disruption. The second is strongest when the goal is to package the application in a smaller, cleaner form that is easier to move, repeat, and recover. Together, the evidence shows a clear tradeoff: the first approach is about controlled changeover, while the second is about making the application more portable and more disciplined to run.

For Nia, the useful shorthand is simple: one approach protects the moment of release, while the other improves the shape of the thing being released.

The practical difference is visible in the results. One test showed that a failed instance was replaced in 3 seconds, which is fast enough to limit the visible impact of a problem. Another test showed that the packaged image dropped from 619 MB in the single-piece version to 50.6 MB in the production version, a reduction of 568.4 MB. That matters because smaller images are quicker to store, move, and start, and they reduce the amount of unnecessary material carried into production. The result is not only a cleaner release artifact, but also a simpler operational footprint.

| Concern | How the blue/green approach addresses it | How the container approach addresses it |
| --- | --- | --- |
| Deployment mechanism | It keeps two live environments ready and moves users from one to the other only after the new version is verified. That makes release day less risky because the old path stays available until the new one is accepted. | It packages the application into a smaller production image that is built once and run the same way each time. The process is more repeatable and less dependent on the machine where it is started. |
| Rollback mechanism | It can send traffic back to the earlier live environment quickly if the new release behaves badly. The rollback is about switching attention back to the known-good version. | It rolls back by deploying the earlier image tag again. That is reliable, but it is not as immediate as a traffic swap because the replacement image must be started again. |
| Failure recovery | It reduces user impact by keeping an alternate live environment available if the active one fails. The strength here is continuity, not automatic repair. | It can recover a failed instance automatically. In the evidence, the replacement came up in 3 seconds, which shows that the platform can restore service quickly after a single instance disappears. |
| Scaling | It can scale, but every additional live environment carries the full weight of the application. That makes the approach safer for release control than for long-term efficiency. | It scales from a leaner image. The production image is 568.4 MB smaller than the single-piece baseline, so each copy is cheaper to store and move, but the approach still needs orchestration to manage many copies well. |

The main board-level takeaway is that the second approach improves operational discipline without yet solving the whole runtime management problem. It makes each release smaller, more predictable, and easier to recover, but it does not by itself decide where multiple copies should run, how they should be distributed, or how they should be coordinated as load changes. That is what the next project, Kubernetes orchestration, adds: it turns a good single deployment unit into a managed fleet with clearer control over placement, recovery, and growth.
